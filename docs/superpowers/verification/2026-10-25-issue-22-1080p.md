# Issue #22 — recognition at 1920×1080: what was measured, what was fixed

**Status: fixed and verified live.** Branch `fix/1080p-recognition`, shipped as 1.1.2.

## The claim in the issue

Augment recognition "fails at 1920×1080" but works at 2560×1440, 1600×900 and 1366×768.
The evidence was a real 4K capture **downscaled** to each width and fed to
`--scan-image`; 1920 was the only width that returned "no augment screen".

## What the still images actually showed

All 17 offer captures from the 25 Oct 4K game plus the redacted 2560×1440 fixture were
replayed through the detector at four widths (INTER_AREA downscale of the source frame,
the way the earlier report was produced).

| Before the fix | 2560 | 1920 | 1600 | 1366 |
|---|---|---|---|---|
| captures read as 3 cards (of 14 legible) | 14 | 14 | 14 | **11** |
| fixture (2560×1440 real capture) | 3 | 3 | 3 | **2** |

Three of the 17 captures are Tab-scoreboard frames, not augment screens; they fail at
every width and always did. So the resolution-specific failure was at **1366**, not 1920:
one capture read none of the cards and another two of three. **1920 did not fail** — not
with any of the 17 captures, not under six resampling filters (AREA, LINEAR, CUBIC,
LANCZOS4, NEAREST, PIL/LANCZOS), and not on a live 1920×1080 frame either.

Conclusion: the 1920 entry in the report was a property of the downscaled file, not of a
1920×1080 game window. The resolution dependence the reporter pointed at was real, but its
visible symptom was at 1366.

## Root cause

`lolhex/vision/detector.py`, full scan:

```python
scale = min(1.0, DETECT_MAX_W / max(1, band.shape[1]))   # only ever downscales
```

The band (0.12–0.88 of the window width) reached the OCR engine as a different image at
every display size:

| Game window | Band width | Pixels sent to OCR |
|---|---|---|
| 3840×2160 | 2919 | 1600×887 |
| 2560×1440 | 1945 | 1600×888 |
| 1920×1080 | 1459 | **1459×810** |
| 1600×900 | 1216 | **1216×675** |
| 1366×768 | 1039 | **1039×576** |

Same card face, five different images, and behaviour that changes per display. At 1039 px
the titles are small enough that Windows.Media.Ocr loses a card on some real frames.

## Fix

`fit_width()` normalises the band to exactly `DETECT_MAX_W` (1600) px in **both**
directions; `detect_scale()` is the shared mapping used to put word boxes back into window
coordinates. Downscale uses INTER_AREA, upscale LANCZOS4 — Lanczos4 was chosen by
measurement: Cubic and Linear each lost a card at the 1600 width on the real corpus,
Lanczos4 did not. The height is truncated, not rounded, so 4K still sends byte-identical
1600×887 pixels to the recogniser.

Result: full-scan band read is now uniform — 37.7/37.2/40.3/40.3/40.1 ms at
3840/2560/1920/1600/1366, against 37.0/37.5/31.1/26.7/21.9 before. The small resolutions
pay up to 18 ms more per scan, and a game only does ~24–39 of them (game 1: 39 × 69 ms
wall, 22 ms CPU). Full suite 554 passed.

## Regression tests

`tests/test_detection_scale.py`:

- five window sizes (3840/2560/1920/1600/1366) must all hand the OCR an image exactly
  `DETECT_MAX_W` wide (fails before the fix at 1920, 1600, 1366);
- the real 2560×1440 fixture, resized to 2560/1920/1600/1366, must read all three cards
  (`2016 / 2138 / 2088`); before the fix the 1366 case read two.

`tests/test_full_scan_badge_bounds.py` now uses the same `detect_scale()` instead of
duplicating the old formula.

## Live game 1 — windowed 1920×1080

`game.cfg` set to `WindowMode=1, Width=1920, Height=1080`. League treats those as the
*window* size, so the client area came up 1904×993; it was resized to exactly 1920×1080
before play (verified each capture is 1920×1080 and the HUD is not stretched — the minimap
stays square).

| Check | Result |
|---|---|
| Augment screens | 4, at 17:37, 17:42, 17:46, 17:48 |
| Badges per screen | 3 on every one — e.g. *Heavy Is The Crown* Best, *Final Form* Consider reroll, *Scopier Weapons* Consider reroll; later *The Boom and the Bass* / *Still Here* / *It's Critical* |
| Errors | 0 — no Traceback/ERROR/识别异常/评估异常 |
| Per-game cost | strips 2,548 × 3 ms, full scans 39 × 69 ms (CPU 22), title OCR 6,958 |
| Calibration | saved for 1920×1080 from the default guess (strip path confirmed it) |

**Did the old code fail this live window?** No. The same live 1920×1080 frames were
replayed through the pre-fix code path: on every stable frame both old and new read the
same three cards. So the issue's "fails at 1920" did not reproduce on a real window; the
fix is justified by the measured pixel dependence and the 1366 losses, not by a live 1080p
failure.

## Champion select

Champion select is a different code path (`vision/champselect.py`) and cannot be proven
from a still, so it was checked live in both games.

| Game | Client window | Result |
|---|---|---|
| 1 (1080p game) | 1600×900 | Cards: the 2-card screen read both (Mordekaiser, Kha'Zix) with win-rate badges; bench 5–7 and team 3–5 heroes recognised across the phase; own hero correct as it changed |
| 2 (4K game) | 2880×1620 | Two-card screen read both; own hero correct |

**Limitation, recorded honestly:** this machine runs a 3840×2160 panel at 150% scaling, so
a 1920×1080 *physical* client is 1280×720 logical and the client's own renderer would not
accept a scripted resize (it kept painting a 1600×900 surface inside a 1920×1080 window,
which is what made the client unusable mid-session earlier). The client was therefore left
at its real size, 1600×900 — **fewer pixels than 1920×1080** and the same fractional
layout. The live 1600×900 capture, resized to 1920×1080, also resolves bench (8), team (5)
and own hero, so 1920×1080 is covered a fortiori but was not itself a live client window.
